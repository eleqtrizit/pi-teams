# Pi Teams decisions

Design decisions for pi-teams and the reasons behind them. Update this file whenever you add or change a decision. AGENTS.md stays limited to the file map and entry points.

## Tool registration and identity

- Tools register in `extensions/index.ts` in three identity blocks: lead tools under `isLead`, shared tools for every session, worker tools under `isWorker`. `isLead` is true when `PI_AGENT_TYPE` is unset or `"lead"`; `isWorker` is true for `"teammate"` or `"readonly-worker"` when the agent is not named `team-lead`.
- `close_myself` registers for workers and for spawned leads (a lead session with a preassigned `PI_AGENT_ID`, i.e. started by `spawn_team_lead`) only. Reason: the interactive top-level lead must never be able to kill itself with one tool call. Before it removes itself, `close_myself` sends a `Closed: <label>` notice to every agent still waiting for a reply, and nothing else. `extensions/index.ts` holds the registration gate; `registerCloseMyself` in `extensions/shared-tools.ts` holds the tool.
- Read-only workers are filtered by pi's `--tools` set at spawn, on top of the registration split. Reason: the extension cannot restrict what a spawned session loads, but the spawn flag can, so the restriction happens at launch.

## Flavors and model resolution

- Flavors are `orchestrator` (orchestrating, planning, coordinating), `worker` (coding), and `swarm` (read-only information gathering), stored as `enabledModelsOrchestrator`, `enabledModelsWorker`, and `enabledModelsSwarm`. `spawn_teammate` picks from `worker` (and `orchestrator` for a planning or coordinating teammate). `spawn_readonly_worker` picks from `swarm`, then `worker`, then the lead's model. The `flavored-models` slash command registers with the team-lead tools and saves through `src/utils/flavoredModels.ts`.
- `migrateLegacyFlavors` converts the legacy `enabledModelsHigh/Med/Fast` keys once at the lead's `session_start` (`high` to orchestrator, `med` and `fast` to worker), shows a warning naming the moved models, and queues the same warning onto the next `get_models` result.
- `pi-oneturnagent` keeps its own read-only reader for both the legacy and current key sets and never migrates. Reason: it only reads the settings; mutating them is reserved for the lead session.
- `resolveModel` walks a priority ladder for bare-name requests: flavored models from pi settings (the union of all three lists) first, then the scoped models (pi `--models` flag, or the enabledModels list when the flag is absent), then the entire registry. The fuzzy match runs only against the first non-empty group. Reason: a configured group always wins over the wider registry. Provider-prefixed requests resolve strictly within the named provider. Resolution handles OAuth provider precedence. Models and thinking level can be overridden per teammate.
- The dollar-prefixed one-turn model substitution inputs (`$<model> <prompt...>` and `$$<model> <prompt...>`) moved to the pi-oneturnagent package (`~/repos/pi/pi-oneturnagent`). pi-teams no longer registers them.

## Stale-write guard

- `extensions/fs-tools.ts` registers hash-guarded `read`, `edit`, and `write` overrides. Every text `read` result ends with a `file_hash: xxxxxxxx` line (first 8 hex chars of sha256 of the bytes). `edit` and `write` require a `fileHash` that matches the current on-disk content; pass `"new"` for a file that does not exist yet. Successful `edit` and `write` results append the fresh hash, so follow-up edits need no extra read. Reason: an agent must never overwrite a file it has not re-read.
- `description` and `fileHash` are schema-optional but required in practice; `requireAll` validates them inside `execute`. Reason: pi core's schema error names only one missing parameter, but a rejection must name every missing one. The rejected partial is stored, and `amend(tool="edit"|"write", fields={...})` merges the missing fields and executes the completed call. A merge that still misses fields keeps the merged partial stored, so a follow-up amend can continue.
- `extensions/bash-hash.ts` registers a `tool_result` handler that detects files a bash command wrote (output redirection and `tee`), verifies each path, and appends `file_hash: <hash> (bash-written: <path>)` lines. Reason: bash can still create files, so the guard covers bash-written files too.
- The tool ordering guarantee (`description` first per parameter) is tested in `extensions/fs-tools.test.ts`.
- The guard moved to this package from pi-journal. pi-journal now journals `edit`/`write` mutations passively from `tool_result` events and registers no tools itself.

## Messaging

- There is no mailbox. `send_message` resolves only after the recipient's extension accepted the message, and fails at once with `RecipientUnreachableError` when the recipient is not running. Reason: a message to a stopped agent is never stored, so the sender learns immediately instead of waiting on a delivery that cannot happen.
- Delivery is direct. The socket listener hands the message body, with from/to/subject/timestamp header, to the extension, which injects it as a user message. Messages that arrive mid-run are queued and flushed as one follow-up at the run boundary. Reason: an arriving message must never interrupt active tool work, and the agent must never call a tool to read its own messages.
- Recipient forms: an 8-character agent id from `list_agents`, one of your worker names, the alias `"lead"` for your lead (workers only), or `"all"` for every visible agent. A broadcast reports unreachable members and still delivers to the rest.
- Visibility rules: a lead sees every lead plus the workers it owns; a worker sees its lead and its siblings. `authorizeSender` in `src/utils/messaging.ts` enforces the same rules on the receiver. Reason: sender-side filtering alone would let a stale or buggy sender address an invisible agent.
- Every send sets the required boolean `expectReply`: `true` when the sender needs an answer (a task, a question, a status request), `false` for replies, reports, and acknowledgments. Every delivered message carries a `fromLabel`, the sender's id, and a `Reply expected:` line derived from `expectReply` (`formatDeliveredMessages` in `extensions/index.ts`).

## Reply obligations (expectReply)

The extension never sends an agent's own text on its behalf; agents report with `send_message`. A sender that needs an answer sets `expectReply: true`, and the extension reminds the recipient until it answers.

- **Recording:** on arrival, `receiveTeamMessage` records an obligation in the session's `ObligationTracker` (`src/utils/obligations.ts`). A newer request from the same sender replaces the subject and resets the reminder count.
- **Clearing:** any `send_message` from the recipient to that sender clears the obligation, whatever its `expectReply` value. A send that fails with `RecipientUnreachableError` also clears it. Reason: the sender is gone, so no reply can exist. The `onMessageSent` and `onRecipientUnreachable` hooks on `SharedToolDeps` connect the tool to the tracker.
- **Reminders:** the `agent_before_settle` handler appends one `custom_message` entry (`customType` `pi-teams-reminder`) naming every waiting sender and returns `continue: true`, at the last point where pi can still continue a run. Reason: the reminder reaches the model as user text in the same run, so the agent stays Busy and no new settle cycle starts. Each obligation gets at most `MAX_REMINDERS` (3) reminders; aborted runs, failed runs, and runs that cannot continue get none.
- **Expiry:** at `agent_settled`, every obligation that reached the cap is removed and its sender receives `No reply from <label>`, with fixed text that never quotes the agent. The notice also releases a `pi -p` lead parked in the run hold.
- **Interruption:** on an aborted run, every waiting sender receives `Interrupted: <label>`. The obligations stay pending, so the next run reminds again.
- **Closing:** `close_myself` sends `Closed: <label>` to every waiting sender before `removeAgent` runs.
- **Loop termination:** a reply sent with `expectReply: false` creates no obligation on the original sender, so a request and its answer end the exchange. Only agents that mark every message as needing an answer can extend it, and the reminder cap bounds each obligation.
- **Notices** are sent with `expectReply: false`, and send errors are ignored. Reason: the recipient can be gone.
- The extension requires Pi 1.1.0 or later. Reason: `agent_before_settle` arrived in Pi 0.87.0 and `aborted` on `agent_settled` arrived in Pi 1.1.0.
- The pure logic is unit-tested in `src/utils/obligations.test.ts`; the handler wiring and end-to-end scenarios (silent worker, early reply, two leads, broadcast, run-hold release) in `extensions/expect-reply.test.ts`.

## Non-interactive sessions (run hold)

When the lead runs `pi -p` (or `--mode json`), pi exits as soon as the run settles, which would strand spawned workers in their panes. The extension holds the run open instead.

- While this lead has live workers in the registry, the `agent_end` handler parks the run. No LLM activity happens while parked. Reason: the hold happens in the extension; sleeping inside bash commands is never used.
- A queued worker message releases the hold and continues the run. Worker reports and the `No reply from`, `Interrupted:`, and `Closed:` notices all arrive this way.
- The hold releases when this lead has no workers in the registry, when no worker has been alive for three consecutive liveness checks (workers need a moment to boot), or when a follow-up is queued.
- Idle workers do not release the hold; completion is the lead's decision, made by calling `close_all_workers` when every teammate has reported back. Reason: only the lead knows whether the overall work is done.
- Worker liveness uses the worker's pid file (written at its `session_start`, before its first turn) as the primary signal, with pane/window probes and the activity marker as fallbacks.
- Spawned workers start as plain pi sessions with no extension flags, so they load their own configured extensions (pi-teams, pi-sandbox). Never add `-ne`. Reason: it drops every configured extension, including the sandbox.
- The decision logic lives in `src/utils/hold.ts` (`shouldHoldWhileTeamActive`, `countLiveWorkers`, `shouldReleaseRun`, all unit-tested). The hold loop checks for queued follow-ups every second; liveness checks run every 5 seconds because terminal probes shell out to the terminal multiplexer.

## Registry, history, and locking

- The registry root lives under `~/.pi/agent/pi-teams/`, in the home directory. Reason: records, sockets, run state, and the `agents.jsonl` history must survive a reboot. The directory has mode 0700 and files 0600. Reason: only your user can read or message your agents.
- `readAgentRecords` trims on load: it checks each record's `cwd`, then removes every dangling record file, its stale socket, and its history entry. Reason: agents whose working directory was deleted disappear from every tool automatically. Set `PI_TEAMS_REGISTRY_DIR` to relocate the root (the test suite uses it for isolation).
- One-shot `pi -p` sessions that were not spawned by pi-teams skip registration when they have no preassigned id and no UI.
- The transport needs no lock. Reason: each message is one connection. Registry writes are atomic (temp file + rename), so two sessions never clobber the same record.
- `agents.jsonl` is shared by every session, so its read-modify-write cycles run under a cross-process lock (`src/utils/filelock.ts`): an exclusive open-file-description advisory lock via the prebuilt N-API addon `fs-native-extensions` on a permanent inode at `agents.jsonl.flock` (flock(2) on macOS, `F_OFD_SETLK` on Linux). The inode is created once and never unlinked or renamed, so the kernel arbitrates every contender; a holder that exits or crashes releases the lock when its descriptor closes. Reason: there is no steal path, no age cap, and no pid identity check, and a reused pid cannot hold a dead process's lock.
- A holder that stays alive but stops progressing (SIGSTOP, debugger, suspended host) keeps exclusive access; contenders get `LockHeldError` at the wait limit (`PI_TEAMS_LOCK_WAIT_TIMEOUT_MS`, default 2 seconds) rather than taking the lock from a live process. Reason: no userland check before a final write can fence an arbitrarily suspended writer. The holder pid written into the file is diagnostics only and never authorizes access.
- Self-healing callers (`writeAgentRecord`, the `readAgentRecords` trim, `removeAgentRecord`, `pruneAndList`) catch `LockHeldError` and `LockUnavailableError` and leave the entry for the next list pass. The read-path trim uses a zero-wait try-lock. Reason: a held lock must never stall message delivery.
- When the addon cannot load (no prebuilt binary for the platform) or the filesystem rejects advisory locking (ENOLCK, ENOTSUP, EOPNOTSUPP, ENOSYS: NFS without lockd, SMB, some FUSE), the failure is a distinct `LockUnavailableError` caught at the same boundaries, so registration, messaging, listing, and teardown keep working without history while one stderr warning on the first history-lock use names the remedy. The trim still removes stale record files and sockets. Reason: deletion eligibility comes from the missing cwd, never from lock state. Skipped history entries self-heal on the next successful sync. Descriptor-level bugs (EBADF) and other kernel errors propagate raw. A critical section never runs without the lock.
- One list pass runs a single locked `syncAgentHistory` transaction (`src/utils/history.ts`): it stamps online records, upserts missing entries for online and surviving records so losses self-heal, drops entries whose record no longer exists in the registry, collapses cwds whose records are all offline (socket-probed) to one entry keyed to the newest surviving record while preserving each directory's newest `lastSeenAt`, and drops entries whose cwd directory is gone. Reason an unhandled orphan would live forever: a cwd with an online record never compacts. A pruned record's entry survives the pass that pruned it and either folds into the cwd's keeper through compaction or drops on the next pass. Entries written or started at or after the probed snapshot are never touched. Reason: they belong to sessions that registered while the probes ran, and their presence blocks compaction of the whole cwd. The shutdown path (`removeAgent`) deletes a history entry only when no surviving record shares its `(cwd, startedAt)` key.
- Upgrading across the flock boundary requires stopping every pi session before starting any new one. Reason: sessions running the old link-based lock and sessions running flock do not exclude each other, on the same path or different paths. The leftover `agents.jsonl.lock` from the old scheme is inert under the new one and is never removed automatically. Reason: a mixed-version session may still hold it through the link protocol; delete it by hand once every session has stopped.
- `.pi/tool.log` is no longer written. Reason: the `edit`/`write` audit trail moved to the separate pi-journal extension.

## Claude Code client

A Claude Code session joins the network as a lead, through the `pi-teams` CLI and a Claude Code mod. Nothing in the socket protocol changed: a lead is a registry record plus a listening socket, and the receiver never checks that the sender is pi.

- **CLI surface** (`src/cli.ts`): `version`, `listen`, `list`, `send`, `spawn`, `spawn-lead`, `close`, `state`, `models`. Output is JSON on stdout; errors go to stderr with exit code 1 (failed), 2 (`RecipientUnreachableError`), or 3 (version check failed). `listen` registers a lead record with `client: "Claude Code"`, runs `adoptOrphanedWorkers`, applies `authorizeSender` to every inbound message, prints `{"type":"ready",...}` then one `{"type":"message",...}` line per message, and exits and unregisters on SIGTERM or when its parent changes (a reparented `process.ppid` is the owner-died signal, because the mod spawns it with stdin closed).
- **Version gate:** every command other than `version` first runs `checkCliVersion`. The extension writes `version.txt` at every `session_start`, before the registration skip. Reason: `-p` sessions write it too. The CLI refuses to run when the file is missing, unparseable, or names a newer version, and its messages give the fix (`pi install` plus starting pi once, or `npm i -g @eleqtrizit/pi-teams-cli`). `src/utils/version.ts` holds the logic; the bundle gets its version from the `__PI_TEAMS_VERSION__` define.
- **Separate npm package:** the CLI ships as `@eleqtrizit/pi-teams-cli`. `npm i -g github:...` installs this whole package including the `pi-taskgraph` dependency tree (about 200 packages) and failed in testing; `pi install` omits dev dependencies, so a `prepare` build is not an option; and the npm name `pi-teams` belongs to the upstream author. `scripts/build-cli.mjs` bundles `src/cli.ts` with esbuild into `cli/pi-teams.cjs` (gitignored) and syncs `cli/package.json`'s version and its `fs-native-extensions` dependency. `fs-native-extensions` stays external. Reason: the history lock must keep working in the installed CLI.
- **Shared code:** `src/utils/launch.ts` and `src/utils/agentList.ts` serve both the extension and the CLI. Model resolution stays in the extension. Reason: only a pi session has a model registry; the CLI requires a fully qualified `provider/model`. `src/utils/spawn.ts` declares `ModelContextLike` instead of importing pi's types, so the CLI bundle needs no pi packages, and `setPiBinaryCommand("pi")` stops `piBinaryCommand()` from launching the CLI itself.
- **`client` field:** `AgentRecord.client` marks a lead registered by a non-pi client; `agentTitle` (`src/utils/agentFormat.ts`) renders it in labels and `list_agents` lines in place of `Pi Agent`.
- **Mod behavior** (`claude-mod/`, listed by `.claude-plugin/marketplace.json`): `hooks/register.ts` starts `pi-teams listen` at `session.start` and, for each message, batches for 300 ms and calls `$.prompt.submit` (not awaited), which starts a turn. A prompt the engine declines after a user interrupt is kept and resubmitted at `turn.complete`. Tools register as `mcp__pi-teams__<name>` and are served by `tool.call` hooks that run the CLI (`hooks/lib.ts`). `turn.start` and `turn.complete` publish busy and idle through `pi-teams state`.
- **Mod guidance ships as a skill** (`skills/network`), not a `prompt.compose` hook. Reason: where the built-in guard `cc-plugin-sec-default` loads (managed settings, or a Team or Enterprise login), a user mod's `prompt.compose` hook never runs. The reply-obligation reminders are not reproduced in the mod.
- **Spawning from Claude** uses the terminal adapter detected from Claude Code's own environment. Reason: workers appear next to the Claude session and inherit `PI_LEAD_ID` = the Claude lead's id.
- **Tests:** `npm test` covers the CLI (`src/cli.test.ts`, including the built binary), `launch.ts`, and `version.ts`. The mod runs against the real engine with `cd claude-mod && command claude plugin test`; use `command claude` because a shell alias that puts options before `plugin` makes it refuse.

## Spawn, lifecycle, and peer leads

- Messages have a UUID, a subject line, a sender identity, a recipient, and a body. Agent ids are ephemeral: they change every session. Reason: use them only for `send_message`; record agents by name and working directory in documents, notes, tasks, and comments.
- `spawn_teammate` and `spawn_readonly_worker` wait up to 30 seconds for the worker's socket before they return. Reason: the child must boot and register before the lead can message it.
- When the socket listener receives a message, the extension delivers it as a user message, which wakes the idle agent for a new turn. Idle state is managed with event-driven timers and a shared mutable context object.
- **Spawn decision rule (encoded in the injected lead prompt, `buildPeerLeadPrompt` in `extensions/index.ts`):**
  - Spawn a peer lead with `spawn_team_lead` when the work belongs to a different directory and needs an independent agent that coordinates its own workers. You cannot close it, so delegate there only for peer-directory work.
  - When the user asks to spawn an agent for another directory, always spawn a team lead, never a teammate. Reason: teammates are for your own directory only.
  - The spawn tools run through the extension, not the agent's sandboxed read and bash tools. A directory that returns "Operation not permitted" when listed is still a valid spawn target. Reason: never refuse to spawn or ask the user to `/sandbox-unlock` just to spawn.
  - For work in your own directory, spawn teammates with `spawn_teammate` (coding) or `spawn_readonly_worker` (research). They join your team, you own them, and you close them with `close_all_workers` when they are done.
- Peer leads are not subordinate to each other. They answer each other with `send_message`; nothing is sent automatically. A lead that needs an answer sets `expectReply: true`, and the receiving lead is reminded until it replies.
- **`list_agents` output:** one line per agent, `Pi Agent in <cwd>: <id>: <status>` for leads and `Worker <name> in <cwd>: <id>: <status>` for workers. Statuses: `Idling` (alive and settled, no run in progress; socket accepts connections and the run-state file is not fresh-busy), `Busy` (mid-run cycle), `Offline` (pid dead or socket not listening). The calling agent is marked `(you)` and always shown as Idling.
- Offline leads are collapsed to one record per directory (the newest by `startedAt`), unless an online lead exists in that directory. Lines are ordered with the viewer's workers first, then everyone else by directory proximity (`pathDistance` in `src/utils/agentFormat.ts`), ties broken by most recent last-online time. `pruneAndList` stamps `lastSeenAt` in `agents.jsonl` for every agent it finds online. Reason: offline peers sort by when they were actually last online, not by when they started.
- `read`/`edit`/`write` results must never record agent ids. Reason: ids are ephemeral; names and working directories identify agents across sessions.
